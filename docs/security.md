# Security posture

What this system defends against, what it does not, and one mechanism that
was requested and deliberately not built.

## Threat model

The machine is a fourteen-year-old laptop that leaves the house. The
realistic threats, in order of likelihood:

1. **Casual access.** Someone picks up an unlocked laptop and changes
   something they should not.
2. **Opportunistic theft.** The laptop is taken. The thief wants the
   hardware and will wipe it; the data is incidental.
3. **Targeted access to the data.** Someone wants what is on the disk
   specifically, and has physical possession.
4. **Accidental self-inflicted damage.** The owner, or a child, or a
   script, does something destructive by mistake.

Threat 4 is the most likely of the four by a wide margin, and any control
that increases it to reduce threat 3 is a bad trade.

## Controls

| Control | Defends against | Does not defend against |
|---|---|---|
| Admin credential (scrypt) | 1 | 3 -- the hash is on the disk |
| Lockout with exponential backoff | 1, online guessing | 3 -- no prompt is involved |
| Hash-chained audit log | undetected tampering | deletion of the whole log |
| Safety floor compiled into the package | policy-file edits, 1 | a determined edit of the package |
| Integrity manifest verified at boot | silent corruption or edits | a manifest regenerated by the attacker |
| **LUKS full-disk encryption** | **2, 3** | an unlocked running machine |

LUKS is the only control in that table that addresses threat 3, which is
why the ISO installer enables it and why everything else is built assuming
it is doing its job. Nothing in userspace can substitute for it: an
attacker with the disk does not type at a login prompt.

## Why failed logins do not wipe the system

This was requested and is not implemented. The reasoning:

**It fires on the wrong events.** Typos, key repeat, a cat on the keyboard,
a child, an autocomplete, a script retrying with a stale credential. Every
one of those is far more frequent than an attack, and each one would
destroy the work.

**It does not fire on the actual threat.** An attacker with physical access
removes the drive, or boots a USB stick, and reads the filesystem directly.
They never reach the login prompt, so the trigger never runs. The mechanism
is invisible to precisely the adversary it was meant to stop.

**It is asymmetric in the wrong direction.** Reliable harm to the owner,
negligible cost to the attacker. That is the definition of a control that
should not ship.

**The wipe would not even work.** Overwriting files on an SSD does not
reliably destroy them: wear levelling means the controller may keep the
original blocks. Meaningful erasure on modern storage means destroying a
key, not overwriting data -- which is to say, it means encryption.

**The desired property is available without it.** "Nobody can read this
without the passphrase" is exactly what LUKS provides, with no destruction
and no false positives.

## If you want a destructive option anyway

There is one responsible form: a **duress passphrase**. You choose a second
passphrase; entering it at the LUKS prompt erases the key slots, making the
disk permanently unreadable. Debian packages this as
`cryptsetup-nuke-password`.

The difference from wipe-on-failure is the whole point:

- it fires only on a **specific string you chose**, never on a wrong guess
- an attacker cannot trigger it by accident, and neither can you
- it destroys a key rather than attempting to overwrite data, so it
  actually works
- the failure mode is "I typed the wrong one of my two passphrases", which
  is rare and entirely within your control

It is still irreversible. There is no recovery, no support call, no
forensic undo. Set it up only with a tested backup elsewhere.

```bash
sudo apt install cryptsetup-nuke-password
sudo dpkg-reconfigure cryptsetup-nuke-password
```

## Credential handling

The admin password is stored as a salted scrypt hash (n=2^14, r=8, p=1) and
never in clear text. It is set by the installer, which prompts; it is not
present in any shipped file, because a credential baked into a distributed
archive is a credential that is already public.

Wrong usernames take the same time to reject as wrong passwords, so the two
cannot be distinguished by timing.

Sessions last fifteen minutes and are required for every command that
changes the policy. Reading the effective parameters needs no session --
knowing what the rules are is not a privilege worth restricting.

## Audit log

Every login, failure, policy change and refused policy change is appended
with the digest of the previous entry. Editing or removing a line
invalidates every line after it, and `nemo admin verify` reports where.

This cannot prevent an attacker with write access from deleting the file
entirely. It makes the realistic case -- quietly removing a single
failed-login record -- detectable. That is the achievable goal on an
unencrypted filesystem, and another reason the encryption matters more than
anything here.
